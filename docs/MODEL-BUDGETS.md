# 模型输入输出与大批量处理规划

适用：厦门广电编辑评馈系统。当前为四平台各 10 篇的真实数据测试；后续数据库统一采用 MongoDB。

## 一、结论

大量数据进入数据库，不等于大量原文一次进入模型。采用“原始数据 → 标准化 → 作品要点 → 评论分批洞察 → 事件汇总 → 增量更新”的处理链。每一步独立限制输入、输出、耗时和重试次数，保留来源 ID 和实际覆盖范围。

事件发现和归并不能只依赖共同关键词；同一城市、栏目或电影节等大话题之下，还应区分具体主体、行动、时间阶段和独立子事件。对于不确定归属，保留未归并状态。

## 二、明确模型服务的实际边界

不能根据“Qwen3.8-27B-FP8”名称推断当前服务的上下文配置。需要确认实际部署的上下文窗口、单次最大生成长度、并发、RPM、TPM、是否启用思考，以及输出预算是否包含思考 token。

每次调用满足：

`系统提示词 + 本次材料 + 历史摘要 + 预留输出 + 安全余量 ≤ 服务实际上下文上限`

安全余量建议至少 2048 token，或上下文窗口的 10%，取较大值。这是规划起点，仍需按服务实际限制调整。

应使用与部署模型一致的 tokenizer 精确计数。JSON、来源编号、提示词、父评论上下文也计入；不能只数正文。模型 usage 可用于调用后统计，不能替代调用前预算。缺少 tokenizer 时先用严格字节/字符限制做保守防护，并明确它不是精确 token 计算。

## 三、建议的任务预算

下表是初期配置建议，**不是当前模型服务已验证的容量**。token 数含完整请求，批量条数只是第二道限制，以先触及的限制为准。前提是部署上下文可以容纳该任务输入、输出和余量。

| 任务 | 输入预算起点 | 输出预算起点 | 第二道限制与处理 |
| --- | --- | --- | --- |
| 连接测试 | 约 200 token 以内 | 256–1024 token | 不发送业务数据；推理模型可能消耗额外思考预算 |
| 作品要点提取 | 6000 token | 800–1200 token | 原文过长按段落分块，再生成作品卡片；保留段落来源 |
| 事件匹配/归并 | 6000–8000 token | 1500–2500 token | 最多 12 张作品卡片，避免直接塞入大量全文；已有事件只给相关候选 |
| 评论分批分析 | 8000 token | 1500–2000 token | 通常最多 80–100 条短评论，长评论或长讨论串时自动减少 |
| 单事件综合分析 | 10000–12000 token | 2500–3500 token | 使用作品卡片、评论批次洞察和代表证据，不重复全部原文 |
| 竞品对比 | 8000–10000 token | 2000–3000 token | 仅比较同一具体事件；按媒体、平台、时间窗口平衡材料 |
| 事件增量更新 | 4000–6000 token | 1000–2000 token | 旧摘要 + 新作品/评论洞察 + 必需上下文，不重复全量历史 |

模型推理预算与最终可读报告长度需要分开管理。对于可选关闭思考的 Qwen/vLLM 服务，可在结构化提取阶段测试关闭思考；正式分析是否保留思考，以结果质量、延迟和预算实测决定。`chat_template_kwargs.enable_thinking` 是特定服务能力，并非所有兼容接口都支持。参考 [Qwen 官方部署文档](https://qwen.readthedocs.io/en/latest/deployment/vllm.html)。

## 四、限制输出结构，减少无用篇幅

报告只输出结构化 JSON，界面渲染 JSON；不在同一请求里再生成完整 Markdown 或 HTML。建议：

- 事件摘要 300–600 个汉字以内。
- 主要关注、疑问、建议、分歧各最多 5–8 项，证据不足为空数组。
- 每项 title 30 字以内、detail 120–200 字以内。
- 每项展示最多 3–5 条代表证据，其余完整证据关系在系统中保存。
- 平台差异最多覆盖实际有样本的四个平台；竞品条目按同事件有效媒体数量控制。
- 跟进建议最多 5 项，区分“待核实”“可补充报道”“继续观察”，不把建议标成已执行。

长 ID 在发送前映射为本次请求的短编号，例如 W001/C001；返回后由系统映射回真实 ID。模型不能创建证据、修改原始数据或以 URL 代替证据 ID。缩短编号只减少复制错误，不改变证据。

## 五、原文与评论怎么分块

作品先保存完整原文。按语义段落拆分，保留标题、发布时间、段落序号与来源 ID，避免把长正文静默截断后当成全文分析。作品卡片保留事件要素、已报道事实、角度和未覆盖信息，不能将猜测写成事实。

评论以讨论串为基本单位。保留根评论、父评论和被回复对象，不能把子评论独立归类后误解立场。超长讨论串可拆分，但每块都带必要祖先语境，并记录重复上下文，避免重复计数。

先去重重复采集记录，不随意删除不同用户的相同观点。海量评论按平台、自有/竞品、时间窗口与讨论主题分层处理。高赞、最新、提问、争议线索均可作为代表证据来源，但不能只取负面或高赞评论后宣称代表全部受众。

当无法处理全量时，明确显示“平台评论统计数 / 实际收录原文数 / 本轮分析数 / 讨论串覆盖数”。按来源原文确定计数，不让模型估算人数、声量或占比。

## 六、事件汇总与增量更新

事件归并先检索少量候选，例如结合时间窗口、实体和内容向量筛出 5–10 个相关事件，再让模型判断；不要把所有历史事件清单带入每次请求。

一个事件有几百篇报道或数万条评论时，先生成作品与评论批次的洞察，再汇总这些洞察。汇总输入中保留代表原话和来源链接，允许回取原文核查，避免摘要反复压缩导致证据丢失。

保存每次分析的输入指纹、材料版本、模型、提示词版本、处理窗口、覆盖数量和证据 ID。只因采集时间更新而内容未变时不重算。只有新增作品、新评论、新事实或规则版本变化才创建相应增量任务。

滚动“最新 10 篇”只是当前测试窗口，不能用于生产历史档案。正式接入后，需要上游分页或游标将实际新增数据持续入库，模型任务独立消费新增/变化数据。

## 七、队列、并发与额度

从单任务并发 1 起步，实际压测后再考虑 2–4；不能把所有事件直接并发调用。分别控制任务队列、每分钟请求数、每分钟 token、每日 token/费用和每事件重复分析频率。

优先级建议：明确的时效性新事实/待核实线索 → 活跃事件增量 → 新事件归并 → 日常复盘 → 历史补算。自动判断的风险线索仍需来源核实，不能以模型分数自动给作品扣分。

预留额度供编辑单次查询和必要的格式修复。任务支持暂停、取消、过期和去重，达到额度时排队或等待下一窗口，不无限重试。多实例部署需要 MongoDB 中的任务租约/去重索引；当前进程内每小时调用计数不能当作生产配额系统。

## 八、异常处理

| 情况 | 处理方式 |
| --- | --- |
| 输入超预算 | 缩小批次，或先生成中间作品/评论洞察，不强行发送 |
| 输出因长度截断 | 不解析半份报告；缩小任务或调整任务输出预算，最多一次有针对性的重试 |
| JSON 或引用无效 | 最多一次格式修复，仍失败则保留失败任务，不写正式结论 |
| 429/服务繁忙 | 按 Retry-After 或退避排队，结合全局限额，避免所有任务同时重试 |
| 超时/网络错误 | 有限重试；每次尝试留记录，不将同一付费请求无期限重复提交 |
| 模型处理中来源变更 | 校验输入版本，旧版本结果不得覆盖新版本分析 |
| 没有评论或竞品 | 对应结果为空并标明缺口，不生成替代内容 |

同一任务建议总重试上限 2 次；格式修复最多 1 次，均计入额度。模型输出中的外部指令只作为材料，不执行。

## 九、MongoDB 需要保存什么

原始作品与评论、互动快照、作品卡片、评论批次洞察、事件归属、模型报告、运行记录、增量游标与编辑改进记录分集合保存。不要把一个大事件的全部评论无限嵌入同一个文档。

对输入指纹 + 模型版本 + 提示词版本建立任务去重约束；每条分析必须能找回当时的来源版本。记录 prompt/completion token、耗时、失败原因和重试次数，不记录密钥。来源全文不写入普通运行日志。

详细集合建议见 [MongoDB 存储规划](STORAGE.md)。

## 十、实施顺序与当前状态

1. **当前已实现**：四平台各 10 篇；归并每批最多 12 篇；正文节选显式标记；短编号映射；证据与事件 ID 校验；格式最多修复一次；超时、可选每小时调用上限（当前设0，不限制次数）；失败不回退虚拟数据。
2. **下一阶段**：确认服务实际上下文与 tokenizer，增加按任务的 token 预算、usage/延迟记录、输入预算预检、逐批结果持久化和任务状态。
3. **接入评论后**：评论串分块、覆盖记录、作品卡片与评论洞察分层汇总，评估证据遗漏和观点偏差。
4. **规模扩大前**：MongoDB、增量游标、任务队列、配额与限流、全局去重和后台调度。

当前服务仍有 16 万字符的请求材料保护和统一输出上限；字符限制不等于精确 token 预算。多层汇总、tokenizer、全局队列与 MongoDB 还属于规划，未宣称已实现。

## 十一、容量和成本如何估算

不要按“作品数量 × 一份完整报告”估算，因为同一材料会经过不同任务，也有缓存命中和失败重试。按任务记录以下账目：

`总输入 token = 各类任务实际输入 token 之和`

`总输出 token = 最终回答 token + 服务计入输出的思考 token`

`云模型费用 = 输入 token × 输入单价 + 输出 token × 输出单价 + 供应商其他计费项`

价格和思考计费方式取决于实际供应商，当前未确认，不填写假定单价。自部署模型则重点记录 GPU 占用、吞吐、排队时间、失败率和部署成本。

先用当前 40 篇真实作品建立每类任务的 token 与耗时分布，再用更多真实时间窗口评估日增作品和评论量。用中位数估算日常需求，用较高分位值预留峰值；不能用一次连接测试耗时推断生产吞吐。

先通过确定性逻辑完成去重、时间/平台过滤、互动计数和分页。旧作品正文未变，不重复提取作品卡片；事件没有新材料，不重写报告。向量检索、全文索引和分批洞察用于减少模型需要阅读的材料量，不能替代完整数据保存。

## 十二、本次真实测试说明

本次使用 `Qwen3.8-27B-FP8`，连接测试成功。一度出现整批 40 篇输出截断及无效作品引用，证明仅增加总输出上限不够；后续采用最多 12 篇的批次、短编号映射与严格校验。

一次归并输出为 20 个候选事件，涉及 32/40 篇作品，8 篇保持未归并。这个数字仅是程序运行结果，不代表归并准确率。电影节等大主题可能被模型归得过宽，生产前必须抽样核对具体事件边界，并支持拆分、关联子事件和重新归并。

已对“厦门广电记者报道进博会现场‘体检’体验”事件的抖音、微博两篇真实作品完成一次模型分析，得到作品总结与后续报道建议。没有评论和竞品材料，相关数组留空。建议里的“受众可能好奇”只能视为编辑假设，不能作为已观测受众需求。模型结果保存在 `work/actual-model-test.md`，用于核对来源，不能作为内容已改进的记录。

规模化前优先验证：事件误合并/漏合并、摘要是否忠于原文、证据是否支持每条结论、评论立场是否脱离上下文、空数据时是否保持空输出、增量变化是否触发恰当重算。格式通过率与内容准确率分开统计。

## 十、当前 Demo 的分步骤事件分析

已按 BettaFish 的分工与审阅思路适配轻量流程：报道梳理 → 受众反馈（有评论才运行）→ 同事件媒体对照（有双方作品才运行）→ 证据审阅与简报。单事件2至4次调用，整任务开始前检查额度；输出上限分别为2400/2800/1800/1600 token，并受 MODEL_MAX_TOKENS 约束。当前小批量材料另有32000字符保护，不是精确 token 计数。上文大批量分块与增量队列仍属规划。实现与限制见 [BettaFish 适配说明](BETTAFISH-ADAPTATION.md)。
