# BettaFish 事件分析参考与适配

调研及适配日期：2026-11-06。面向厦门广电编辑，服务于同一事件的报道复盘、受众聆听与后续内容改进。

## 参考依据

本轮读取了 [BettaFish README](https://github.com/666ghj/BettaFish)、[InsightEngine](https://github.com/666ghj/BettaFish/blob/main/InsightEngine/agent.py)、[ForumEngine 主持流程](https://github.com/666ghj/BettaFish/blob/main/ForumEngine/llm_host.py)、[报告篇幅预算](https://github.com/666ghj/BettaFish/blob/main/ReportEngine/nodes/word_budget_node.py)和[报告结构校验](https://github.com/666ghj/BettaFish/blob/main/ReportEngine/ir/validator.py)。这是对读取时主分支的观察，不代表对整个项目的部署或效果评测。

BettaFish 将私域数据研究、外部检索、媒体分析、论坛讨论与报告生成组织为多个环节。适合参考的是分工、交叉审阅、篇幅约束和结构校验。厦门广电已经有作品接口，首版应围绕现有证据推进分析，避免重复建设采集体系。

| 参考设计 | 本 Demo 的适配 | 当前边界 |
| --- | --- | --- |
| 专项研究 Agent | 报道梳理、受众反馈、同事件媒体对照三个角色 | 同一配置模型分别执行，数据缺失时跳过 |
| Forum 主持与交叉审阅 | 审阅原文与候选发现，选择保留项，再生成简报 | 一轮审阅，不开展无限反思循环；不等于独立事实核验 |
| 报告预算节点 | 分步骤限制输出与发现条数 | 使用实际服务支持的输出参数，输入字符限制不等于精确 token 预算 |
| 报告 IR 验证 | 统一 JSON 报告、短证据编号、引用校验后渲染 | 不让模型直接生成页面 HTML |
| 多来源研究 | 自有/竞品作品及评论作为证据，热榜仅作背景 | 暂不增加外网搜索或音视频识别依赖 |

## 已实现的事件分析流程

1. **报道梳理**：总结报道信息和各平台侧重，识别可能混入的不同事件，提出具体的补充报道方向。此步骤不把作品评论数转换为受众观点。
2. **受众反馈**：有真实评论原文才运行。归纳关注、疑问、建议及分歧，发现待核实线索。每条发现必须引用评论原文，保留父子评论语境。
3. **同事件媒体对照**：同时有自有、竞品作品才运行。每项比较必须包含双方证据。受众反应差异仍需双方评论支持，不能只比较点赞或评论统计数。
4. **证据审阅与简报**：模型看到原文和编号后的候选发现，只能保留或排除候选，不能新增/改写发现；摘要须依据材料并说明数据缺口。服务端核对返回的候选编号及最终证据引用。

单事件最多4次调用；当前无评论与竞品时仅2次。任何一步失败，整个新报告不保存，原有有效报告保留。没有后台无限循环或自动重试。整个流程串行占用模型任务锁，每个专项最多调用一次。当前默认 `MODEL_MAX_CALLS_PER_HOUR=0`，不限制每小时调用次数。若配置正整数限额，仍会在第一步前检查完整流程所需额度；该可选计数在服务进程内，生产阶段应进入 MongoDB/队列持久化。

页面新增“分析过程与数据覆盖”，显示完成与跳过原因、材料数量和候选发现保留/排除数。不展示模型内部推理，不把“已审阅”标成“事实已确认”。

## 当前测试预算

| 步骤 | 请求的最大输出 token | 候选发现限制 |
| --- | --- | --- |
| 报道梳理 | 6000 | 三个数组合计最多15项 |
| 受众反馈 | 6000 | 五个数组合计最多15项 |
| 媒体对照 | 6000 | 最多15项 |
| 审阅与简报 | 1600 | 只选择已有候选；摘要最多600字 |

每步实际请求上限取表内值与 `MODEL_MAX_TOKENS` 的较小值。以上是请求预算，不是模型服务已验证的上下文容量，也不是实际消耗量；是否包含思考 token 取决于部署服务。当前尚未持久化 provider usage 或统计费用。

当前单事件最多40篇作品、100条评论。完整材料 JSON 超过32000字符会在调用前停止，不静默截断；审阅材料超过64000字符也停止。字符限制是小批量保护，不是 tokenizer。后续大量数据应按作品/评论串分批提取，再做事件汇总，不能直接放宽此限制。详见 [模型预算规划](MODEL-BUDGETS.md)。

短编号仅用于本次模型请求：作品 W001、评论 C001、发现 F001。输出还原真实证据 ID 后存储，页面可返回原文。模型版本包含新流程版本、模型地址/名称与关键生成配置，新旧结果缓存分开。

## 数据缺口与后续发展

当前作品接口提供四平台各10条真实数据，但没有评论原文、竞品及百度/头条热点接口，因此对应专项能力只能用隔离测试验证协议，不能宣称已验证真实受众分析效果。后续优先补齐评论串与竞品数据，再做事件边界、引用支持度、疑问提取和媒体对照的标注评测。

扩大规模时采用 MongoDB 保存原文、事件归属、分析批次、证据关系及改进记录；后台调度与增量队列是下一阶段建设项。当前自动分析仍只在工作台页面打开时运行。
